# Plan: FMI Event Mode Support

Based on the investigation in `docs/investigation-fmi-event-modes.md`, this
document proposes concrete changes to add proper FMI event mode support to the
bouncing ball and establish patterns for future event-driven models.

## Overview

Three areas of work, in dependency order:

1. **adml-solver** — Add an event-aware solver to the shared solver crate
2. **bouncing-ball** — Refactor to use event indicators, `event_update()`, and
   the new solver
3. **Documentation** — Update AGENTS.md with guidance for future event models

---

## Step 1: Event-Aware Solver in `adml-solver`

**File:** `crates/adml-solver/src/lib.rs`

The existing `euler_step()` does plain integration with no event detection. Add a
new function and corresponding macro that integrate zero-crossing detection into
the micro-step loop, following the same pattern as the Reference-FMUs
`cosimulation.c` solver.

### New public function: `euler_step_with_events`

```rust
pub fn euler_step_with_events<M: UserModel + ModelGetSetStates>(
    model: &mut M,
    context: &mut dyn Context<M>,
    current_communication_point: f64,
    communication_step_size: f64,
    fixed_step: f64,
) -> Result<CSDoStepResult, Fmi3Error>
```

**Algorithm:**

```
allocate prev_z[MAX_EVENT_INDICATORS], z[MAX_EVENT_INDICATORS]
evaluate initial event indicators into prev_z

for each micro-step:
    1. Forward Euler step (same as euler_step)
    2. Evaluate event indicators into z
    3. Check for sign changes: any(prev_z[i] * z[i] < 0)
    4. If sign change detected:
       a. Call model.event_update(context, &mut event_flags)
       b. If event_flags.values_of_continuous_states_changed:
          re-read states from model (they were modified by event_update)
       c. Re-evaluate indicators into z (post-event state)
    5. Copy z into prev_z
```

This keeps event detection internal to the CS step, matching the Reference-FMUs
approach. The model defines *what* the indicators are and *what* happens at an
event; the solver handles *when* to check and *how* to orchestrate.

### New macro: `euler_cs_step_with_events!`

```rust
macro_rules! euler_cs_step_with_events {
    ($fixed_step:expr) => {
        fn do_step(
            &mut self,
            context: &mut dyn fmi_export::fmi3::Context<Self>,
            current_communication_point: f64,
            communication_step_size: f64,
            _no_set_fmu_state_prior_to_current_point: bool,
        ) -> Result<fmi_export::fmi3::CSDoStepResult, fmi::fmi3::Fmi3Error> {
            $crate::euler_step_with_events(
                self, context,
                current_communication_point,
                communication_step_size,
                $fixed_step,
            )
        }
    };
}
```

### Design notes

- The function needs `M::MAX_EVENT_INDICATORS` to size the indicator arrays.
  This constant is available on the `Model` trait (generated by `FmuModel`
  derive). However, `euler_step_with_events` currently only bounds on
  `UserModel + ModelGetSetStates`. We need to also bound on `Model` to access
  `MAX_EVENT_INDICATORS`, or add the constant to `ModelGetSetStates`. The
  simplest approach: add a `Model` bound.

- When `MAX_EVENT_INDICATORS == 0`, the function should degrade to plain
  `euler_step` with no overhead (compile-time check, no allocations).

- The `event_update()` call needs a `&dyn Context<M>` (immutable). This is
  the same signature as in the `UserModel` trait. The solver already has
  `&mut dyn Context<M>` so it can reborrow as `&dyn Context<M>`.

- `CSDoStepResult::event_handling_needed` should remain `false` — events are
  handled internally within the step. This matches the Reference-FMUs CS
  approach. Setting it `true` would require the CS master to enter event mode,
  which is more complex and not needed for this use case.

- Future refinement: bisection to locate the exact crossing time within a
  micro-step. Not needed for the initial implementation (1ms steps give
  sufficient accuracy for the bouncing ball, matching Reference-FMUs which also
  uses `FIXED_SOLVER_STEP = 1e-3`).

## Step 2: Refactor Bouncing Ball

**File:** `models/mechanical/bouncing-ball/src/lib.rs`

### 2a. Add event indicator field

Add a field to hold the event indicator value and mark it with the
`event_indicator` attribute:

```rust
#[variable(event_indicator = true, skip)]
event_indicator_h: f64,
```

This makes `MAX_EVENT_INDICATORS = 1` in the generated `Model` impl, which is
reported to ME integrators via `fmi3GetNumberOfEventIndicators`.

Note: `skip` keeps it out of the FMI variable list (it's internal bookkeeping).
If the derive macro doesn't support combining `event_indicator` with `skip`,
the alternative is to just use a plain `#[variable(skip)]` field and manually
set `MAX_EVENT_INDICATORS` (would require checking if that's possible with the
current derive macro). This needs to be verified during implementation.

### 2b. Implement `get_event_indicators()`

```rust
const EVENT_EPSILON: f64 = 1e-10;

fn get_event_indicators(
    &mut self,
    _context: &dyn Context<Self>,
    indicators: &mut [f64],
) -> Result<bool, Fmi3Error> {
    // Hysteresis: when h is near zero and ball is moving up,
    // keep indicator negative to prevent retriggering
    if self.h > -EVENT_EPSILON && self.h <= 0.0 && self.v > 0.0 {
        indicators[0] = -EVENT_EPSILON;
    } else {
        indicators[0] = self.h;
    }
    Ok(true)
}
```

This matches the Reference-FMUs approach exactly. The indicator is positive when
the ball is above ground and goes negative on impact. The hysteresis region
prevents chattering immediately after a bounce (when `h` is near zero but `v` is
now positive).

### 2c. Implement `event_update()`

Move the collision logic out of `do_step()` into the proper callback:

```rust
fn event_update(
    &mut self,
    _context: &dyn Context<Self>,
    event_flags: &mut EventFlags,
) -> Result<Fmi3Res, Fmi3Error> {
    event_flags.reset();

    if self.h <= 0.0 && self.v < 0.0 {
        self.h = f64::MIN_POSITIVE;
        self.v = -self.v * self.e;

        if self.v < self.v_min {
            self.v = 0.0;
            self.h = 0.0;
            self.stopped = true;
        }

        event_flags.values_of_continuous_states_changed = true;
    }

    Ok(Fmi3Res::OK)
}
```

**Note on `stopped` flag:** The current implementation uses `stopped` to halt
the integration loop. With the event-aware solver, the stopping behavior should
work via `event_flags.terminate_simulation = true` or by setting `g = 0` (as
the Reference-FMUs do). Setting `g = 0` is simpler — it makes the ball stay at
rest without needing a separate flag. However, keeping the `stopped` flag is
also fine since it's internal. Choose whichever is cleaner during
implementation.

### 2d. Replace custom `do_step()` with the new macro

```rust
adml_solver::euler_cs_step_with_events!(0.001);
```

This replaces the entire 50-line custom `do_step()`. The collision logic now
lives in `event_update()` and `get_event_indicators()`, and the solver handles
orchestration.

### 2e. Update the standalone `do_step` (testing helper)

The `impl BouncingBall` block has a standalone `do_step()` method for unit tests
that don't use the FMI context. This should be updated to match the new event
logic, or tests should be refactored to go through the FMI interface. Simplest
approach: keep the standalone method but have it call the same indicator/event
logic.

### 2f. Update tests

Existing tests should still pass since the physics are identical. Verify:
- `test_collision_handling` — velocity reversal with restitution
- `test_stopping_condition` — ball stops below v_min
- `test_energy_loss_on_bounce` — energy decreases

Add new tests:
- `test_event_indicator_positive_above_ground` — `indicators[0] > 0` when `h > 0`
- `test_event_indicator_negative_at_ground` — `indicators[0] <= 0` when `h <= 0`
- `test_event_indicator_hysteresis` — `indicators[0] = -epsilon` when `h ~ 0, v > 0`
- `test_event_update_reverses_velocity` — direct test of `event_update()`
- `test_event_update_sets_flags` — `values_of_continuous_states_changed` is true after bounce

## Step 3: Documentation Updates

### 3a. Update AGENTS.md

In the "Solver choices" section (around line 77-80), add the event-aware macro:

```markdown
**Solver choices:**
- `adml_solver::euler_cs_step!(step)` - Forward Euler (most models)
- `adml_solver::symplectic_euler_cs_step!(step)` - Symplectic Euler (Hamiltonian systems)
- `adml_solver::euler_cs_step_with_events!(step)` - Forward Euler with zero-crossing event detection
- Custom `do_step` - For models that need something beyond the above
```

### 3b. Add event model guidance to AGENTS.md

Add a section explaining how to implement a model with events:

```markdown
### Models with Events (Hybrid Systems)

For models that have discrete state changes triggered by continuous state
conditions (e.g., collisions, saturation limits, mode switches):

1. **Identify the event condition** as a zero-crossing function. The function
   should be positive on one side of the event and negative on the other.
   Example: for a ground collision, use `h` (height) — positive above ground,
   negative below.

2. **Add an event indicator field** to the struct:
   ```rust
   #[variable(event_indicator = true, skip)]
   event_indicator_name: f64,
   ```

3. **Implement `get_event_indicators()`** to compute the indicator value.
   Add hysteresis near zero to prevent chattering:
   ```rust
   fn get_event_indicators(
       &mut self,
       _context: &dyn Context<Self>,
       indicators: &mut [f64],
   ) -> Result<bool, Fmi3Error> {
       indicators[0] = self.h; // positive = no event, sign change = event
       Ok(true)
   }
   ```

4. **Implement `event_update()`** to handle the discrete state change:
   ```rust
   fn event_update(
       &mut self,
       _context: &dyn Context<Self>,
       event_flags: &mut EventFlags,
   ) -> Result<Fmi3Res, Fmi3Error> {
       event_flags.reset();
       if /* event condition */ {
           // Apply discrete state change
           event_flags.values_of_continuous_states_changed = true;
       }
       Ok(Fmi3Res::OK)
   }
   ```

5. **Use the event-aware solver macro:**
   ```rust
   adml_solver::euler_cs_step_with_events!(0.001);
   ```

This approach:
- Works for both ME and CS interfaces
- ME integrators get proper event indicators via `fmi3GetEventIndicators`
- CS mode detects events internally via zero-crossing checks at each micro-step
- Matches the Reference-FMUs architecture
```

## Out of Scope (Future Work)

- **Bisection for exact event time:** The current approach detects events at
  micro-step boundaries (1ms resolution). Bisection within a micro-step could
  locate the exact crossing time. Not needed now — matches Reference-FMUs
  accuracy.

- **`event_handling_needed` signaling to CS master:** The current plan handles
  events internally in CS mode. If a future use case requires the master to
  participate in event handling (e.g., to change inputs at the event), the
  solver could be extended to return `event_handling_needed = true` and the
  event time as `last_successful_time`.

- **Time events:** `EventFlags::next_event_time` supports scheduled time events.
  No current model needs this, but the infrastructure is ready.

- **`fmi-export` TODO for CS event mode after init:** `common.rs:93-94`
  hardcodes `event_mode_used = false`. This only affects the state transition
  after `exit_initialization_mode()` — it doesn't block event handling during
  simulation. Could be addressed upstream if needed.

- **Symplectic Euler with events:** Could add
  `symplectic_euler_step_with_events()` if a Hamiltonian system needs event
  detection (e.g., pendulum with hard stops).
